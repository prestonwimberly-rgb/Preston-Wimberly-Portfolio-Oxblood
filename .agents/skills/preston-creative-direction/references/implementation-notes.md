# Implementation Notes

## Repository entry

1. Read repository instructions and the current content model before editing.
2. Inspect the site structure, configuration, design tokens, assets, routes, build scripts, and quality commands.
3. Identify the audience, conversion goal, strongest existing work, available evidence, factual constraints, image rights, and unresolved claims.
4. Check the working tree and preserve unrelated user changes.

## Editing priorities

1. Fix inaccurate or unsupported claims.
2. Fix accessibility and usability failures.
3. Clarify content hierarchy and reading order.
4. Improve image selection, crop, caption, and provenance.
5. Refine typography, spacing, proportion, and material cues.
6. Add motion or decoration only when it has a clear job.

Prefer a small set of high-confidence edits to an unearned wholesale redesign. Do not remove factual content merely to manufacture whitespace; edit, sequence, or restructure it first. Treat image choice and crop as information architecture. Do not simulate aging or damage in CSS or image processing.

## Responsive and accessible behavior

- Preserve editorial hierarchy on mobile instead of collapsing everything into identical cards.
- Keep navigation obvious, tap targets large enough, focus visible, contrast sufficient, alt text useful, and motion reduced when requested by the operating system.
- Test the project's documented desktop, mobile, and narrow-phone widths.
- Preserve static or server architecture constraints unless the user explicitly authorizes a change.

## Verification

Run the repository's documented quality gate. Inspect the built output and representative routes. Check overflow, reading order, crop behavior, links, metadata, scripts, performance, keyboard use, focus, semantics, labels, alternative text, contrast, and reduced motion.

Score authenticity, editorial hierarchy, material character, evidence, restraint, usability, performance, and accessibility from 1 to 5. Fix the weakest category first.

Report remaining factual, rights, technical, or accessibility risks plainly.
